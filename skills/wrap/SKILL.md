---
name: wrap
description: 제출 전 필수 파일·실행·검증·저장 상태를 점검하고 결과 공유 메시지 초안과 수동 제출 순서를 안내. 사용자가 직접 부를 때 쓴다.
---

문서 경로는 PLAN.md의 매핑을 따르고, 매핑이 없으면 기본 경로를 쓴다. 과제 지정 양식이 같은 역할이면 REQUIREMENTS.md·DECISIONS.md 대신 그 파일을 쓴다.

PLAN.md의 제출물 확정 목표 10분 전에는 사용자에게 제출을 시작하도록 안내한다. 제출물 확정 전까지만 이 스킬을 수행한다. 각 항목을 실제로 확인하고 체크리스트로 보고한다.

- 과제 README의 필수 파일명·경로·내용과 요구사항 문서의 모든 Must를 대조한다. 누락은 무엇을 고칠지 먼저 알리고 보완하며, 미구현은 이유를 남긴다.
- README의 실행 방법으로 최종 핵심 경로를 한 번 확인한다. 이미 유효한 검증 근거는 PLAN.md를 참조하며 전체 테스트·변형 검증을 반복하지 않는다.
- README 원문 아래에 문제 정의·실행 방법·기능·한계를 적고 중요한 선택의 근거와 미검증이 기록됐는지 확인한다. 새 보고 문서를 중복 생성하지 않는다.
- 비밀정보 후보는 `rg -l --hidden -i 'api[_-]?key|secret|token|password' -g '!.git/**' -g '!.agents/**' -g '!node_modules/**' .`처럼 파일명만 찾는다. rg가 없으면 파일명만 출력하는 대안을 쓴다. 결과 없음과 명령 실패를 구분하고, 실제 값은 출력하지 않는다. 이 검색만으로 비밀정보 검증을 마쳤다고 주장하지 않는다.
- 디버그 파일·임시 산출물(`work/`)·.env가 제출·커밋에 섞이지 않았는지 확인한다. 본인이 띄운 검증 프로세스만 정리하고 화면 확인에 필요한 서버는 유지한다.
- 로컬 커밋하고 `git status`를 확인한다. push·외부 공유는 하지 않는다. 시간이 부족하면 커밋보다 필수 파일 저장과 제출을 우선한다.
- 업무 담당자에게 보낼 **결과 공유 메시지 초안**(5줄 이내): 무엇을 만들었는지, 어떻게 받는지(전달 방법·파일), 어떻게 쓰는지, 담당자가 알아야 할 한계, 다음 단계. 전달 방법을 아직 정하지 않았다면 메시지에 질문으로 넣는다. 전송은 사용자가 한다.

사용자에게 제출 순서를 짧게 안내한다. AI가 화면을 조작하거나 제출했다고 주장하지 않는다.

1. 편집기의 저장 상태와 필수 경로를 직접 확인한다.
2. 플랫폼 안내에 따라 제출 내용을 미리 확인하고, 고칠 것이 있으면 확정 전에 고친다.
3. 제출물 확정은 사용자가 직접 한다. 이후 파일 수정과 AI를 통한 답변·첨삭·코칭을 하지 않는다.
4. 확정 뒤의 절차와 완료 확인은 플랫폼 안내를 따른다.

결과는 `제출 준비 상태 / 남은 필수 조치 / 미검증·한계 / 결과 공유 메시지 초안`으로 보고한다.
