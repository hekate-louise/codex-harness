업무 담당자 인터뷰를 도와줘. 사용자가 함께 적은 내용이 `check`로 시작하면 **보내기 전 점검**, `record`로 시작하면 **답 기록**을 해. 둘 다 아니면 어느 쪽인지 물어봐.

## check: 보내기 전 점검
질문은 사용자가 쓴다. 너는 고쳐 쓰지 말고 점검과 제안만 해.

1. `REQUIREMENTS.md`의 인터뷰 기록(§6)과 가정·질문 목록을 먼저 읽어
2. 질문마다 아래를 표로 보여 줘: 질문 / 문제 / 제안
   - 이미 답을 받은 질문이면 언제 받은 답인지 적고 빼자고 제안
   - 한 문항에 질문이 둘 이상이면 쪼개자고 제안
   - 무엇을 묻는지 막연하면 무엇이 빠졌는지 짚어 줘 (예: "정리"가 폴더 구성인지 파일 이름인지)
   - 장면·사례·실물 요청, 선택지, 구체적인 예시를 붙이면 더 정확한 답이 나올 질문이면 그 방법을 제안
3. 질문이 4개를 넘으면 우선순위를 제안하고, 이번에 보낼 3~4개를 고르게 해
4. 지금 질문으로 확인되지 않는 중요한 빈칸(사용자 환경, 입력·출력, 성공 기준, 꼭 되어야 하는 것, 경계 사례)이 있으면 한 줄로 알려 줘

## record: 받은 답 기록
1. `REQUIREMENTS.md` §6에 다음 번호로 질문 / 답변 요약 / 반영을 추가해. 답변은 업무 담당자의 말을 바꾸지 말고 요약하고, 핵심 문장은 따옴표로 남겨
2. 답 때문에 바뀌는 곳을 갱신해: Must·Should·하지 않을 것, 가정(해소되면 취소선 + 근거), 질문 목록(해결 표시)
3. 영향 확인 결과를 보고해:
   - 기준 출력이나 기존 테스트가 바뀌어야 하는지
   - 새로 필요한 테스트(특히 경계 사례)
   - 코드 변경이 필요한지. 필요하면 바로 고치지 말고 변경 범위만 제안해
4. 범위나 기술 선택이 바뀌었으면 `$decide`로 기록할지 물어봐
5. 바꾼 줄을 보여 줘
