# SK하이닉스 해커톤 Codex 하네스

필수 요구를 놓치지 않고, 입력부터 출력까지 실제로 작동하는 결과물을 만든 뒤, 선택 이유와 검증 근거를 본인이 설명하기 위한 하네스다. 과제 README와 플랫폼 실제 안내가 우선한다.

## 설치와 시작
제공 작업 공간의 과제 루트에서 실행한다. 아래 명령은 Bash·Git이 있는 환경을 전제로 한다.

```bash
git clone https://github.com/hekate-louise/codex-harness work/codex-harness
bash work/codex-harness/install.sh .
```

설치기는 AGENTS.md, 기록 템플릿 3개와 스킬 13개를 복사한다. 기존 파일·스킬은 덮어쓰지 않는다. 기존 AGENTS.md가 있으면 두 파일의 원칙을 검토해 병합해야 한다. 이미 설치한 버전은 재실행만으로 갱신되지 않는다. 공개 저장소에 이 변경이 반영되어야 Clone으로 받을 수 있다.

스킬이 안 보이면 Codex를 다시 시작한다. 플랫폼의 쓰기 제한은 우회하지 말고 허용된 설치 방법을 확인한다. 본 과제에 체험 파일이 유지된다고 가정하지 않는다.

한 번에 시작하는 요청:

> $hackathon 과제 README와 제공 파일을 확인하고 필수 요구를 모두 추적해줘. 먼저 입력부터 출력까지 작동하는 작은 흐름을 만든 다음 필수 기능을 확장하고, 검증·기록·제출 준비까지 진행해줘. 업무 정답이나 범위를 바꾸는 질문만 해줘.

개별 스킬을 순서대로 호출할 필요는 없다. 계획만 원하면 계획만 요청한다. 이미 진행 중이면 기존 기록·코드에서 이어가며 환경 점검과 계획 작성을 처음부터 반복하지 않는다.

## 실제 운영
1. 모든 Must·제출 파일·출처를 확인하고 대표 입력과 기대 출력을 확보한다. 가장 먼저 만들 작은 흐름과 전체 필수 요구는 구분한다.
2. 전체 시간이 주어졌다면 첫 40분 안에 최소 흐름을 실행하는 것을 목표로 한다. 기존 환경을 활용하고 새 도구 설치·UI 장식보다 실행 위험을 먼저 확인한다.
3. 각 필수 기능을 추가할 때 바로 정상·예외를 실행하고 요구 ID에 검증 근거를 연결한다. 중요한 오답 하나는 별개 기준으로 검산한다.
4. 남은 30분에는 선택 기능보다 Must 누락·최종 통합 실행·문서·이해도 점검을 우선한다. 약 10분간 막혔으면 새 근거와 핵심 경로 영향을 보고 조사 지속 여부를 판단한다.
5. 제출물 확정 목표 10분 전부터 저장·미리보기·확정을 준비한다. UI·메신저·제출은 사용자가 직접 조작한다.

단계별 고정 시간표 대신 실행 결과와 남은 시간으로 진행을 조정한다. 위 40분·30분·10분은 권장 판단 기준이며 필수 요구를 포기하는 근거가 아니다.

## 시간 계산
작업 최대 180분, 후속 서술형 6문항×5분, 전체 종료는 한국시간 14:00이다. 준비 대기는 약 5분 안내지만 10분 표시·재시도가 있을 수 있다.

이 하네스는 준비 여유를 기본 15분으로 잡아 `확정 목표 = min(작업 타이머 종료, 13:15)`로 권장한다. 제출 준비는 그보다 10분 전이다. 이 여유가 지연을 보장하지 않으며 실제 화면 안내가 우선한다. 이미 목표 시각을 넘겼다면 즉시 남은 필수 조치를 정리해 제출을 우선한다.

| 시작 예시 | 작업 종료 | 확정 목표 | 제출 준비 시작 |
|---|---|---|---|
| 10:00 | 13:00 | 13:00 | 12:50 |
| 10:30 | 13:30 | 13:15 | 13:05 |

현재 시각·플랫폼 타이머는 확인해서 기록하고 추측하지 않는다. 사전 체험 15분에서는 설치·스킬 인식, 작은 실행·Browser 수동 확인, 저장·감독 연결·종료 흐름을 우선한다.

## 기록과 보조 스킬
- REQUIREMENTS.md: 모든 요구의 ID·출처·기대 동작, 담당자 답과 가정.
- PLAN.md: 시간 기준, 요구→구현 위치→검증 근거→상태, 다음 행동과 중요한 실패.
- DECISIONS.md: 중요한 선택·이유·버린 대안·한계.

과제 지정 문서가 같은 역할이면 그 파일에 기록하고 PLAN.md에 경로를 둔다. 필수 문서가 독립적으로 이해되도록 필요한 요약은 허용하지만 결과·수치를 여러 곳에서 별도로 관리하지 않는다.

`hackathon`은 전체 진행의 진입점이다. `env`, `kickoff`, `interview`, `plan`, `decide`, `verify`, `wrap`, `explain`, `handoff`는 특정 단계가 필요할 때 직접 호출할 수 있다. `grilling`, `diagnosing-bugs`, `frontend-design`은 요청 내용에 맞을 때만 적용한다. 핵심 흐름과 검증은 보조 스킬 호출 여부와 관계없이 수행한다.

## 규정과 하네스 선택의 구분
매뉴얼: 제공 Codex·허용 모델 사용, Astra·개인 API 키·외부 AI 연결 금지, 공개 자료 반입 허용, 문제·파일·결과물 반출과 Git Push 금지, Computer Use 전 단계 금지, 후속 서술형 AI·복사/붙여넣기 금지. 서버는 0.0.0.0에 바인딩하고 플랫폼 Browser에서 사용자가 확인한다.

하네스 선택: UI 자동화까지 사용하지 않고 터미널·HTTP와 수동 화면 확인을 조합한다. 준비 여유 15분, 최소 흐름 우선, 질문을 한 번에 최대 3개로 묶기, 약 10분 후 디버깅 지속 여부 판단은 운영 전략이다. 대회에서 명시한 의무나 성능 보장이 아니다.

Astra 제한 등 응시 규칙은 실제 응시 환경에 적용한다. 대회 전 이 하네스 자체를 검토·개발하는 작업과 혼동하지 않는다. 제출물 확정 뒤에는 파일 수정과 AI 답변·첨삭·코칭을 중단하고, 사용자가 서술형을 마친 후 최종 완료 화면을 확인한다.

근거: 참가자 제공 「시험 필수확인사항 브리프」, 「Proctor 설치 및 촬영가이드」, 「사전 체험 및 응시환경 상세 가이드」(2026-10-28 확인). 원문 PDF·개인 링크·시험 문제는 포함하지 않는다. 실제 제공 환경에서 설치·스킬 호출·모델 행동을 점검해야 하며 형식 검증만으로 효과가 입증되지는 않는다.
