# Codex 작업 하네스

제한 시간 안에 업무 과제의 필수 요구를 놓치지 않고, 입력부터 출력까지 실제로 작동하는 결과물을 만든 뒤, 선택 이유와 검증 근거를 본인이 설명하기 위한 하네스다. 과제 README와 작업 플랫폼의 실제 안내가 우선한다.

## 설치와 시작
과제 루트에서 실행한다. Bash·Git이 있는 환경을 전제로 한다.

```bash
git clone https://github.com/hekate-louise/codex-harness /tmp/h && bash /tmp/h/install.sh .
```

`/tmp`에 쓸 수 없으면 과제 폴더 안 `work/`에 받는다. 설치기가 `.gitignore`에 `work/`를 넣으므로 작업 저장소에 섞이지 않는다.

```bash
git clone https://github.com/hekate-louise/codex-harness work/codex-harness && bash work/codex-harness/install.sh .
```

설치기는 AGENTS.md, 기록 템플릿 3개, 스킬 13개를 복사하고 `.gitignore`에 `work/`를 추가한다. 이미 있는 파일·스킬은 덮어쓰지 않는다. 기존 AGENTS.md가 있으면 두 파일을 비교해 합친다. 설치한 뒤 Codex를 다시 시작한다. 플랫폼의 쓰기 제한은 우회하지 말고 허용된 설치 방법을 확인한다.

한 번에 시작하는 요청 예:

> $hackathon 과제 README와 제공 파일을 확인하고 필수 요구를 정리해줘. 업무 담당자에게 물을 질문 초안과 계획을 먼저 보여 주고, 내가 승인하면 작은 흐름부터 구현해줘. 시작 시각은 ○○:○○, 마감은 ○○:○○이야.

개별 스킬을 순서대로 호출할 필요는 없다. 이미 진행 중이면 기존 기록·코드에서 이어가며 환경 점검과 계획 작성을 처음부터 반복하지 않는다.

## 진행 방식
1. 모든 Must·제출 파일·출처를 확인하고 대표 입력과 기대 출력을 정한다. 업무 담당자에게 사용자 환경·입력·출력을 먼저 묻는다.
2. 범위와 계획을 사용자가 승인한 뒤 구현한다. 승인 뒤의 단계 전환은 묻지 않고 단계가 끝날 때 `한 것 / 근거 / 사용자가 정할 것`을 보고한다.
3. 전체 180분이면 첫 40분 안에 최소 흐름을 실행하는 것을 목표로 한다. 새 도구 설치·UI 장식보다 실행 위험을 먼저 확인한다.
4. 각 필수 기능을 추가할 때 바로 정상·예외를 실행하고 요구 ID에 검증 근거를 연결한다. 중요한 오답 하나는 구현과 별개인 기준으로 검산한다.
5. 남은 30분에는 선택 기능보다 Must 누락·최종 통합 실행·문서·이해도 점검을 우선한다. 한 문제에 약 10분 막히면 멈추고 사용자와 계속 여부를 정한다.
6. 제출물 확정 목표 10분 전부터 저장·커밋·결과 공유 메시지·제출을 준비한다. 화면 확인·메신저·제출은 사용자가 직접 한다.

40분·30분·10분은 판단 기준이며 필수 요구를 포기하는 근거가 아니다.

## 시간 기준
시작할 때 사용자가 시작 시각과 마감 시각(또는 남은 시간)을 알려 주면 PLAN.md에 적는다. 하네스는 `확정 목표 = 마감 15분 전`, `제출 준비 시작 = 확정 목표 10분 전`을 권장한다. 플랫폼 안내가 다르면 그것을 따른다. 시각은 확인해서 기록하고 추측하지 않는다.

## 기록과 보조 스킬
- REQUIREMENTS.md: 모든 요구의 ID·출처·기대 동작, 담당자 답과 가정.
- PLAN.md: 시간 기준, 진행 기록(시각·단계·사용자 결정), 요구→구현 위치→검증 근거→상태, 중요한 실패.
- DECISIONS.md: 중요한 선택·이유·버린 대안·한계.

과제 지정 문서가 같은 역할이면 그 파일에 기록하고 PLAN.md에 경로를 둔다. 결과·수치를 여러 곳에서 따로 관리하지 않는다.

| 스킬 | 호출 | 하는 일 |
|---|---|---|
| `hackathon` | 직접 | 전체 흐름 안내 (시작 → 승인 → 구현 → 마무리) |
| `env` | 직접 | 개발 환경 점검, 사용자 환경 질문 |
| `kickoff` | 직접 | 과제 분석, Must·질문 초안, REQUIREMENTS 기록 |
| `interview` | 직접 | `check`: 보내기 전 질문 점검 / `record`: 받은 답 기록 |
| `plan` | 직접 | 계획을 PLAN.md에 저장하고 승인 받기 |
| `decide` | 직접 | DECISIONS.md에 결정 기록 |
| `verify` | 직접 | 실행·독립 검산·근거 기록 |
| `wrap` | 직접 | 제출 전 점검, 결과 공유 메시지 초안 |
| `explain` | 직접 | 제출 확정 전 이해도 점검 (모범 답안 없음) |
| `handoff` | 직접 | 세션을 바꿀 때 `docs/handoff-NN.md`로 인계 |
| `grilling` | 자동 | 계획·결정의 허점 점검 |
| `diagnosing-bugs` | 자동 | 막힌 버그를 재현 → 가설 → 검증으로 진단 |
| `frontend-design` | 자동 | 화면 디자인 방향 |

## 하네스가 스스로 정한 원칙
화면·브라우저 자동 조작을 쓰지 않고 터미널·HTTP 검증과 사용자의 화면 확인을 조합한다. 과제 데이터를 외부로 보내지 않고 push하지 않는다. 웹 서버는 0.0.0.0에 바인딩한다. 확정 목표 15분 여유, 최소 흐름 우선, 질문은 한 번에 3개까지, 약 10분 막히면 판단하기는 운영 전략이며 성능을 보장하지 않는다. 응시 규정은 플랫폼 안내를 따른다.
